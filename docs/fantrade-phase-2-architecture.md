# Fantrade Phase 2 Architecture: Market & Exchange Foundation

## Executive Summary

This document establishes the production architecture for Fantrade Phase 2, fulfilling the requirements for **Prompt 3: Foundation + Market & Exchange Engine**.

Fantrade is an institutional-grade football ownership economy platform. Previously, Phase 1 existed as a static HTML prototype generated by Python scripts, storing mock financial data in browser `localStorage`. Phase 2 replaces all simulated economics with a centralized, ACID-compliant **PostgreSQL** database, an authoritative **Double-Entry Ledger**, an immutable **Ownership & Share Reservation Engine**, and a deterministic **Matching Engine** based on strict FIFO price-time priority.

## 2. Future Blockchain Compatibility

Per Section 1 and Section 2 of the specification:
- Fantrade is **centralized PostgreSQL** today.
- **NO blockchain, NO smart contracts, NO Web3 wallets (e.g. MetaMask), and NO on-chain $FTR** are implemented.
- The business logic is architected with clean domain service boundaries so that persistence is decoupled from database specifics.

### Service / Repository Decoupling

```
   [ Domain Service: OwnershipService ]
                     |
                     v
   [ Repository Interface: IOwnershipRepository ]
                     |
        +------------+------------+
        |                         | (Future Modular Expansion)
        v                         v
[ PostgreSQL Prisma Adapter ]   [ Blockchain / ERC-1155 / Substrate Adapter ]
```

All share transfers, mints, and reservations occur via `IOwnershipService` and `ILedgerService`. Future on-chain settlement will merely implement an alternate adapter implementing the same transactional interface without requiring changes to the Matching Engine, Order Book, or UI layers.

## 3. Database Schema (PostgreSQL / Prisma)

The database schema is defined in `prisma/schema.prisma` with Decimal(18, 4) numeric precision for all monetary values and exact integers for share counts:

1. **User & Auth**: `User`, `AuthSession` with secure token authentication and status flags.
2. **Assets**: `Asset` (PLAYER vs COACH), `PlayerProfile`, `CoachProfile`, enforcing total shares, circulating shares, and treasury shares.
3. **Ownership**: `Holding` (quantity, availableQuantity, lockedQuantity, averageCost), `ShareReservation` (purpose: ORDER, FANPLAY, SWAP).
4. **Ledger**: `Wallet`, `LedgerAccount` (USER_AVAILABLE, USER_RESERVED, PLATFORM_FEES, PLATFORM_TREASURY), `LedgerEntry` (DEBIT, CREDIT with immutable transaction groups).
5. **Exchange & Orders**: `Market`, `Order` (BUY/SELL, LIMIT, PENDING/OPEN/PARTIALLY_FILLED/FILLED/CANCELLED/REJECTED), `Trade`, `TradeFill`.
6. **Swaps**: `Swap` record tracking atomic asset-to-asset trades with dust refunds.
7. **Market Data**: `PriceHistoryPoint` aggregating OHLC candles across real intervals (`1m`, `5m`, `15m`, `1h`, `4h`, `1d`).
8. **Security & Audit**: `IdempotencyRecord`, `FeeConfiguration`.

## 4. The 10,000,000 Share Rule & Ownership Integrity

### The Invariant
Every Fantrade player and coach asset has **exactly 10,000,000 shares**, with zero exceptions.
- Shares are never minted from thin air during secondary trading.
- At any point in time:
  $$\text{User Owned Shares} + \text{Treasury Shares} + \text{Explicit Locked Custody Shares} \equiv 10,000,000$$

### Ownership Holdings
A user holding tracks:
- `quantity`: Total shares owned by the user.
- `availableQuantity`: Shares free to be sold, swapped, or entered into FanPlay.
- `lockedQuantity`: Shares locked in active resting limit SELL orders or FanPlay reservations.
- **Invariant**: $\text{quantity} = \text{availableQuantity} + \text{lockedQuantity}$.

## 5. Centralized $FTR Double-Entry Ledger

The native currency of the platform is **$FTR**.
- Wallet balances are **never** mutated arbitrarily.
- Every economic movement is recorded in a double-entry transaction where:
  $$\sum \text{Debits} \equiv \sum \text{Credits}$$
- Balance of any account is deterministically derived:
  $$\text{Balance} = \sum \text{Credits} - \sum \text{Debits}$$

### Ledger Transaction Example (BUY Trade Settlement)
When User A (Buyer) matches with User B (Seller) for 100 shares @ 10.00 $FTR:
1. **Gross Value**: 1,000.00 $FTR
2. **Buyer Fee (0.4%)**: 4.00 $FTR
3. **Seller Fee (0.4%)**: 4.00 $FTR
4. **Seller Net Proceeds**: 996.00 $FTR

**Balanced Ledger Entries:**
- DEBIT `User A Reserved Account`: 1,004.00 $FTR
- CREDIT `User B Available Account`: 996.00 $FTR
- CREDIT `Platform Fees Account`: 8.00 $FTR
- **Sum Debits**: 1,004.00 $FTR
- **Sum Credits**: 1,004.00 $FTR
- **Net Imbalance**: 0.00 $FTR

## 6. Real Order Book & Deterministic Matching Engine

### Order Book Derivation
No synthetic depth, sine-wave formulas, or fake liquidity exists.
- **Bids**: Open BUY orders sorted by `limitPrice DESC, createdAt ASC` (highest price first; earlier order first).
- **Asks**: Open SELL orders sorted by `limitPrice ASC, createdAt ASC` (lowest price first; earlier order first).

### Deterministic Matching Policy
1. **Crossing Condition**: Matching occurs whenever $\text{Incoming Bid} \ge \text{Resting Ask}$ or $\text{Incoming Ask} \le \text{Resting Bid}$.
2. **Execution Price Policy**: **The trade executes at the maker's resting limit price**.
   - *Rationale*: If a resting sell order is posted at 10.00 $FTR, and an incoming buyer submits an aggressive limit buy at 11.00 $FTR, the trade fills at 10.00 $FTR. The difference (1.00 $FTR per share) is promptly refunded to the buyer's available FTR account.
3. **Self-Trade Prevention (§26)**:
   - If an incoming order crosses an open resting order belonging to the **same user ID**, the matching engine immediately aborts the cross, cancels the incoming order, releases the reservation, and throws `SelfTradeError`.
   - Wash trading is strictly rejected.

### Atomic Database Settlement
Matching, share transfer, FTR transfer, fee allocation, reservation decrements, and trade creation are encapsulated inside a single atomic `prisma.$transaction`. If any constraint fails, the entire match rolls back to prevent half-settled states.

## 7. Fee Model & Platform Treasury

- Default trade fee is **0.4%**, inherited from the Phase 1 prototype and stored in `FeeConfiguration`.
- Configurable per action type: BUY, SELL, SWAP.
- Documented per specification: *"0.4% is inherited prototype configuration and remains subject to final economic approval."*
- All deducted fees are credited to the `PLATFORM_FEES` ledger account.

---

## 8. Dynamic Asset Swap Engine

The Swap Engine allows exchanging shares of Asset A directly for Asset B:
1. Calculates market value of Asset A shares based on last trade price.
2. Deducts configurable swap fee (0.4%).
3. Calculates maximum whole shares of Asset B receivable.
4. Atomically transfers Asset A shares from user to treasury, transfers Asset B shares from treasury to user, deducts the fee to platform fees account, and refunds the fractional dust in $FTR to user's available wallet balance.
5. Employs idempotency keys to prevent duplicate swap execution.
